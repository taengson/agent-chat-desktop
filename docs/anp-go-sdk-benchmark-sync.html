v2 기반 구현 진행 중 · main은 v2 전용

ANP Go SDK 기반 벤치마크 동기화

장치 신원·결과 서명·1:1 종단 간 암호화가 있는 새로운 v2 동기화를 설계하고 구현합니다. 이전 LAN v1은 별도 태그에만 보관합니다.

목적 키와 신원 페어링 동기화 구현 순서 결정할 사항

무엇을 바꾸려는가

태그 benchmark-sync-v1은 기존 LAN 전용 v1 구현을 보존합니다. main에서 개발할 v2는 한 장치가 외부 HTTPS 주소를 제공하고, 다른 장치가 그 주소로 직접 연결합니다. 사람은 처음 연결할 때만 상대 장치의 fingerprint를 확인하고, 이후에는 장치 키가 요청·결과를 검증합니다.

현재 구현: main에서 v1 LAN 코드·화면을 제거하고 태그 benchmark-sync-v1에 보관했습니다. ANP Go SDK v1.0.3, OS 비밀 저장소의 Ed25519/X25519 장치 키, 변조를 거절하는 서명 envelope, 완료된 결과 proof, 앱이 직접 여는 TLS 1.3 수신 endpoint, 그리고 128비트 초대 secret·요청/응답 서명·양쪽 fingerprint 승인 페어링까지 추가했습니다. E2EE 전송과 실제 pull/push가 다음 단계입니다.

장치 신원

IP·장치 이름·토큰이 아니라 고정 공개키로 연결한 PC를 식별합니다.

결과 원본성

보고서나 다른 PC를 거쳐도, 누가 만든 결과인지와 변조 여부를 검증합니다.

암호화 통신

1:1 E2EE 세션으로 벤치마크 본문을 암호화합니다.

범위: 외부 HTTPS 주소를 제공하는 신뢰한 두 장치가 벤치마크 결과만 교환합니다. 자동 탐색, 공개 Discovery, 릴레이 서버, 그룹 동기화, 대화·첨부·API 키 동기화는 이번 범위에서 제외합니다.

키와 장치 신원

키는 앱을 시작할 때마다 만들지 않습니다. 사용자가 처음으로 보안 동기화 초대 만들기 또는 보안 동기화에 연결하기를 누르면, ensureDeviceIdentity()가 기존 키를 확인하고 없을 때만 생성합니다.

장치 키 준비와 실패 처리

flowchart TD
    start[사용자가 보안 동기화 시작] --> existing{유효한 장치 키가 있는가?}
    existing -->|예| verify[비밀 저장소의 키와 공개 정보를 대조]

    verified -->|아니오| repair[중단하고 키 복구 또는 재페어링 안내]
    existing -->|아니오| create[SDK로 서명 키·암호화 키·prekey 생성]
    create --> storeSecret[개인키를 비밀 저장소에 먼저 저장]
    storeSecret --> persisted{모든 비밀값 저장 성공?}
    persisted -->|아니오| cleanup[생성값 정리 후 오류 안내]

    storePublic --> ready

Ed25519 서명 키 쌍첫 보안 동기화, 장치당 한 번HTTP 요청·벤치마크 결과 서명공개키만
X25519 암호화 신원 키 쌍첫 보안 동기화, 장치당 한 번Direct E2EE 초기 세션공개키만
서명된 prekey첫 시작, 만료 전 교체상대가 내 암호화 세션을 시작하도록 준비공개키·ID·서명만
일회용 prekey 20개첫 시작, 5개 아래면 보충각 새 세션에 한 번만 사용사용할 공개키 하나만
ratchet 상태페어링 확정 때마다메시지 순서·재전송 방지와 E2EE아니오

장치 개인키, prekey 개인값, ratchet 상태는 OS 키체인 또는 플랫폼 비밀 저장소에만 둡니다. TLS 개인키는 사용자가 선택하거나 앱이 새 파일에 만든 PEM 파일에서 앱이 직접 읽고, 일반 JSON 설정 파일에는 PEM 경로·상대 공개키·fingerprint·외부 HTTPS 주소·신뢰 시각처럼 공개 설정만 기록합니다.

키가 바뀌면: 같은 장치 ID가 다른 공개키를 제시하면 동기화를 멈추고 재페어링합니다. 과거 결과를 새 키로 소급 서명하지 않으며, 이전 공개키를 보관한 장치는 이전 proof를 계속 검증할 수 있습니다.

HTTPS TLS 파일 준비

장치 신원 키와 HTTPS TLS 키는 다릅니다. 장치 신원은 v2 화면을 처음 열 때 OS 비밀 저장소에 자동 생성됩니다. 이를 다시 만들면 이미 승인한 장치와 결과 proof가 새 fingerprint를 신뢰하지 않으므로 일반 화면에 재생성 버튼을 두지 않습니다.

  1. 외부 HTTPS 주소(예: https://sync.example.com)를 입력합니다.
  2. TLS 키·CSR 만들기를 눌러 개인키 PEM과 인증서 요청(CSR)을 각각 새 파일로 저장합니다. 기존 파일은 덮어쓰지 않습니다.
  3. CSR을 공개 CA 또는 조직 CA에 제출해 도메인 인증서를 발급받습니다.
  4. 발급된 인증서와 방금 만든 개인키를 파일 선택 창에서 고른 뒤 수신을 시작합니다.
주의: 앱은 상대 PC가 기본으로 신뢰할 수 있는 자체 서명 인증서를 만들지 않습니다. 실제 장치 간 연결에는 공개 CA 또는 조직 CA의 인증서가 필요합니다.

페어링: 사람이 무엇을 확인하고, 앱은 무엇을 검증하는가

페어링은 토큰을 교환하는 과정이 아닙니다. 상대 공개키를 받고, 양쪽 사람이 fingerprint를 비교하고, 그 뒤에 1:1 암호화 세션을 만드는 과정입니다.

A는 외부 HTTPS 초대를 만든 PC, B는 그 주소로 연결하는 PC입니다.

sequenceDiagram
    autonumber

사람이 보는 화면

A: 초대 만드는 쪽

외부 HTTPS 주소, 128비트 일회용 secret, A fingerprint를 보여 줍니다. 연결 요청이 오면 B의 이름·주소·fingerprint와 승인 버튼을 보여 줍니다.

B: 연결하는 쪽

초대 링크 또는 URL·secret을 입력하면 B fingerprint를 보여 줍니다. A의 대기 응답을 받으면 A fingerprint를 확인하게 합니다.

두 사람

전화·메신저·직접 대화처럼 신뢰할 수 있는 별도 방법으로 두 화면의 fingerprint를 비교합니다. 다르면 거절합니다.

B가 보내는 페어링 요청의 핵심

{
  "protocolVersion": 2,
  "requestID": "pair_01...",
  "pairingSecret": "128비트 이상의 일회용 무작위 값",
  "requester": {
    "deviceID": "dev_b...",
    "displayName": "B의 Mac",
    "signing": { "keyID": "ed25519:sha256:...", "publicKey": "...", "fingerprint": "3T4Q-8M9V-…" },
    "encryption": { "identityPublicKey": "..." }
  }
}

요청에는 B의 개인키가 들어가지 않습니다. B가 세션을 시작하는 쪽이므로 A가 승인한 뒤 A의 signed prekey와 일회용 prekey 하나를 받습니다.

한 단계라도 실패하면 연결·신뢰 정보·세션을 만들지 않습니다.

flowchart TD
    request[페어링 요청 수신] --> valid{secret·요청 서명·body digest·요청 ID가 유효한가?}
    valid -->|아니오| reject[거절하고 요청 삭제]
    valid -->|예| compare[양쪽 화면에 상대 fingerprint 표시]
    compare --> matched{사람이 별도 경로로 fingerprint 일치를 확인했는가?}
    matched -->|아니오 또는 취소| reject
    matched -->|예| prekey[A의 prekey를 B에 전달]
    prekey --> session{X3DH 세션 생성과 session-confirm 복호화에 성공했는가?}
    session -->|아니오| reject
    session -->|예| persist{신뢰 정보와 ratchet 상태를 안전하게 저장했는가?}
    persist -->|아니오| reject
    persist -->|예| connected[connected: 암호화 동기화 허용]

외부 HTTPS 정책

A는 https://sync.example.com처럼 DNS 이름과 공개 CA 또는 조직 CA 인증서를 제공해야 합니다. B는 초대에서 받은 URL에만 연결하고, 표준 TLS 호스트 이름·인증서 체인 검증을 통과해야 합니다.

  1. http://와 raw IP 주소는 v2 원격 연결에 사용하지 않습니다.
  2. 일상적인 인증서 갱신을 막지 않도록 TLS leaf certificate는 고정하지 않고, 장치 서명 공개키를 고정합니다.
  3. /pair는 128비트 일회용 secret, 만료, 한 번 사용, rate limit을 적용합니다.
  4. 신뢰 장치 요청 서명이 없는 경로는 장치·벤치마크 정보를 제공하지 않습니다.

일반 화면은 단순하게, 세부 과정은 감사 로그로

일반 화면에는 연결됨, 마지막 동기화, 검증된 결과 수, 조치 필요만 보여 줍니다. 키 생성·fingerprint 확인·서명 실패·세션 오류처럼 자세한 과정은 이 PC에만 남는 구조화된 감사 로그에서 확인합니다.

이벤트로그에 남기는 정보절대 남기지 않는 정보
키 생성·복구·교체시각, 결과, 짧은 fingerprint개인키, prekey 개인값
페어링·승인·거절·만료방향, peer key ID, 결과 코드pairingSecret, 전체 초대 URL
HTTPS·서명 검증 실패호스트명, 실패 범주, request ID digest인증서 원문, Authorization 값
E2EE 세션·동기화세션 ID digest, 건수, 중복·충돌·검증 상태ratchet 상태, 평문·암호문 본문, API 키

로그는 동기화하지 않으며, 기본적으로 최대 1,000건 또는 180일까지만 보관합니다. 사용자는 민감정보를 제외한 진단 로그만 내보낼 수 있습니다.

연결 뒤의 동기화

동기화는 E2EE envelope 안에 서명된 결과를 넣어 전송합니다. 요청을 보낸 장치와 결과를 최초 생성한 장치는 다를 수 있으므로, 요청 서명과 결과 proof를 각각 검증합니다.

flowchart LR
    pull[A가 E2EE pull 요청 전송] --> verifyB[B가 요청 서명·replay ID·E2EE 세션 검증]
    verifyB --> recordsB[B가 서명된 결과 묶음을 E2EE로 응답]
    recordsB --> verifyA[A가 복호화 후 각 결과 proof·충돌 검사]
    verifyA --> saveA[A가 검증된 결과만 저장]
    saveA --> push[A가 자신의 결과를 E2EE push로 전송]
    push --> verifyAonB[B가 동일한 검증과 병합 수행]
    verifyAonB --> logs[양쪽 활동 로그에 결과 기록]

수신 순서

  1. 외부 HTTPS 주소의 호스트 이름과 인증서 체인을 표준 TLS로 확인한다.
  2. HTTP 요청 서명과 고정된 요청자 공개키를 확인한다.
  3. message ID, 만료 시각, replay 여부를 확인한다.
  4. E2EE envelope를 해제하고 ratchet 상태를 안전하게 저장한다.
  5. 각 결과의 원본 proof와 모델 형식을 검증한다.
  6. 현재 fingerprint·원본 ID 충돌 규칙으로 중복·충돌을 처리하고, 성공한 기록만 sync 출처로 저장한다.

결과 wrapper

{
  "version": 2,
  "record": { "...": "ModelBenchmark 원본 내용" },
  "origin": { "deviceID": "dev_...", "keyID": "ed25519:sha256:...", "signedAt": "..." },
  "proof": { "type": "ed25519-signature-2020", "payloadDigest": "sha256:...", "signature": "base64url..." }
}

로컬 ID, 가져온 상태, 전송 상대 이름처럼 장치마다 바뀌는 값은 서명 대상에서 제외합니다. 필드 순서·UTF-8·시간·숫자 표기를 고정해 만든 정규화 JSON의 SHA-256 digest를 서명합니다.
